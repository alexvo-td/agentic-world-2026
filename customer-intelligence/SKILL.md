# Customer Intelligence Suite

A unified React dashboard combining three views in a single `render_react` call: **Buried Treasure (Hidden Trends)** → **Campaign Profitability Assessment** → **Segment Overlap & Recommendations**. Top-level nav switches between views; each view has its own sub-tabs.

## When to Use This Skill

- User asks for "customer intelligence", "hidden trends", or "campaign profitability"
- User wants to analyze a parent segment for cross-division patterns
- User asks "which campaigns should I invest in" or "where are the hidden opportunities"
- User wants trend analysis combined with campaign ROI projections and segment recommendations
- User asks to "find hidden patterns" or "analyze customer data for insights"
- User asks about "segment overlap", "unsegmented customers", or "what segments should I build"

## Prerequisites

- **tdx CLI** for `tdx ps desc`, `tdx query`, `tdx ps list`
- **A CDP parent segment** with customer attributes and behavior tables

## Output File Naming — Unique Filenames Required

**Never overwrite an existing dashboard.** Every generated HTML file must have a unique name combining the company/segment name and a timestamp. Generate the filename at the start of the rendering phase:

```
$(pwd)/{company}_ci_dashboard_{YYYYMMDD_HHMM}.html
```

Examples:
- `tumi_ci_dashboard_20260428_1435.html`
- `pacsun_ci_dashboard_20260428_0912.html`

When using the Write tool, derive the company name from the active CDP parent segment or database name (e.g., `tumi_demo_2` → `tumi`). Always use today's date and current time in `YYYYMMDD_HHMM` format.

## Environment Detection

Before rendering, detect which environment you are running in:

- **Treasure Studio**: The tool `render_react` (or `mcp__tdx-studio__render_react`) is available. Use it to render the React dashboard as described below.
- **Treasure AI Studio** (or any environment without `render_react`): Generate a **self-contained HTML file** instead. The HTML must:
  1. Be a **single file** — no CDN links, no external CSS/JS. Everything inline.
  2. Use **vanilla JS + DOM manipulation** — no React, no JSX, no Recharts, no framework imports.
  3. **Inline all styles** in a `<style>` block. Translate Tailwind classes into plain CSS. Use CSS variables for theming.
  4. **Preserve all interactive features** — top-level page switcher, sub-tabs, hover effects, click-to-expand cards, glassmorphism design — using vanilla JS event listeners.
  5. **Recreate charts as inline SVG** — bar charts, heatmaps, and pie charts should be rendered as SVG elements generated by vanilla JS, not Recharts.
  6. Embed the data object as `const DATA = <JSON>;` in a `<script>` block.
  7. Include a dark/light theme toggle.
  8. Write to `$(pwd)/{company}_ci_dashboard_{YYYYMMDD_HHMM}.html` using **chunked Bash writes** (see pattern below), then open with `mcp__tas__open_file`.

**How to detect:** Check your available tools at the start of the rendering phase. If `render_react` is in your tool list, use it. If not, generate self-contained HTML.

### Chunked Writing Pattern (TAS — REQUIRED)

**Never use the Write tool for the HTML file in TAS.** The file is too large and will time out. Instead, split the file into 5–6 Bash calls using `cat >` (first chunk) and `cat >>` (all subsequent chunks). Each chunk must be ≤ 150 lines.

```
CHUNK 1 — DOCTYPE, <head>, <style> block (CSS variables, resets, layout, glassmorphism)
CHUNK 2 — Remaining CSS (charts, cards, buttons, animations), close </style>, open <body>, header HTML
CHUNK 3 — const DATA = {...}; (the full data JSON object) inside <script>
CHUNK 4 — Helper functions: renderTrends(), renderCampaign(), initCharts(), event listeners setup
CHUNK 5 — renderOverlap(), recommendation cards, push/URL reveal logic
CHUNK 6 — Page router (switchPage), init call, close </script>, </body>, </html>
```

Template:
```bash
# Chunk 1 — head + styles (overwrite/create)
cat > "$FILEPATH" << 'CHUNK1'
<!DOCTYPE html>
<html lang="en">
<head>...
<style>
  /* CSS variables, reset, layout, glassmorphism ... */
</style>
CHUNK1

# Chunk 2 — remaining CSS + body open
cat >> "$FILEPATH" << 'CHUNK2'
  /* charts, cards, buttons, animations ... */
</style>
<body>
<div id="app">...header HTML...</div>
CHUNK2

# Chunk 3 — data JSON
cat >> "$FILEPATH" << 'CHUNK3'
<script>
const DATA = {
  /* full data object */
};
CHUNK3

# Chunk 4 — helper + chart functions
cat >> "$FILEPATH" << 'CHUNK4'
function renderTrends() { ... }
function renderCampaign() { ... }
function initCharts() { ... }
CHUNK4

# Chunk 5 — overlap + recommendation rendering
cat >> "$FILEPATH" << 'CHUNK5'
function renderOverlap() { ... }
function buildRecommendationCards() { ... }
CHUNK5

# Chunk 6 — router, init, close tags
cat >> "$FILEPATH" << 'CHUNK6'
function switchPage(p) { ... }
switchPage(0);
</script>
</body>
</html>
CHUNK6
```

**Rules:**
- Use `CHUNK1`, `CHUNK2`, … as heredoc delimiters (no quotes needed if no `$` inside the chunk, but use `<< 'CHUNKn'` to be safe with any literal `$` in CSS/JS).
- Never put a chunk larger than ~150 lines in a single Bash call.
- If a section (e.g., the DATA JSON) exceeds 150 lines, split it across two consecutive `cat >>` calls with matching open/close structure.
- Run all chunks sequentially (they depend on each other).

**Why unified?** In Treasure Studio, `render_react` replaces the previous artifact — multiple calls would lose earlier dashboards. In AI Studio, a single self-contained HTML file keeps everything in one output. Either way, a single component with page/sub-tab state keeps everything accessible.

## Workflow

### Phase 1: Data Discovery

```bash
tdx ps list
tdx ps desc "Parent Segment Name" -o /tmp/ci_schema.json
```

Read the JSON and categorize columns:
- **Identity**: email, cdp_customer_id (note: first_name may be NULL in many segments)
- **Segmentation**: loyalty_tier, membership_type, subscription_status
- **Value**: predicted_ltv, realised_ltv, monetary, total_spend, aov
- **Engagement**: frequency, recency, session_count, email_opens
- **Churn**: churn_prediction, churn_risk, cart_abandon_rate
- **NBA**: next_best_action, next_best_channel, next_best_product, next_best_offer
- **Behavior tables**: behavior_ecommerce_orders, behavior_email_send, behavior_engagement, etc.

**Critical**: Check column population rates before querying — some columns may be all-NULL:
```sql
SELECT COUNT(*) as total, COUNT(first_name) as has_first, COUNT(email) as has_email,
       COUNT(loyalty_tier) as has_tier, COUNT(category_affinity) as has_affinity
FROM customers
```

### Phase 2: Hidden Trends Queries (run in parallel)

Adapt column names to the discovered schema. Run all queries concurrently.

**Query 1 — Churn paradox:**
```sql
SELECT churn_prediction as status, COUNT(*) as cnt,
  ROUND(AVG(predicted_ltv), 0) as avg_ltv, ROUND(AVG(rewards_points), 0) as avg_points
FROM customers WHERE churn_prediction IS NOT NULL GROUP BY churn_prediction
```

**Query 2 — Tier inversion:**
```sql
SELECT loyalty_tier as tier, COUNT(*) as customers,
  ROUND(AVG(predicted_ltv), 0) as avg_ltv, ROUND(AVG(rewards_points), 0) as avg_points
FROM customers WHERE loyalty_tier IS NOT NULL GROUP BY loyalty_tier ORDER BY avg_ltv DESC
```

**Query 3 — NBA × channel cross-analysis:**
```sql
SELECT next_best_channel, next_best_action, COUNT(*) as customers,
  ROUND(AVG(predicted_ltv), 0) as avg_ltv
FROM customers WHERE next_best_channel IS NOT NULL AND next_best_action IS NOT NULL
GROUP BY next_best_channel, next_best_action ORDER BY avg_ltv DESC LIMIT 15
```

**Query 4 — Category affinity:**
```sql
SELECT category_affinity, COUNT(*) as customers,
  ROUND(AVG(predicted_ltv), 0) as avg_ltv
FROM customers WHERE category_affinity IS NOT NULL GROUP BY category_affinity
```

**Query 5 — Email campaign performance (join sends + opens):**
```sql
SELECT s.campaign_name, COUNT(DISTINCT s.cdp_customer_id) as sent,
  COUNT(DISTINCT o.cdp_customer_id) as opened,
  ROUND(CAST(COUNT(DISTINCT o.cdp_customer_id) AS DOUBLE) / NULLIF(COUNT(DISTINCT s.cdp_customer_id), 0) * 100, 1) as open_rate
FROM behavior_email_send s
LEFT JOIN behavior_email_open o ON s.cdp_customer_id = o.cdp_customer_id AND s.campaign_name = o.campaign_name
WHERE s.campaign_name IS NOT NULL GROUP BY s.campaign_name ORDER BY sent DESC LIMIT 10
```

**Query 6 — Ecommerce by tier (AOV):**
```sql
SELECT c.loyalty_tier, COUNT(DISTINCT e.cdp_customer_id) as shoppers,
  ROUND(AVG(e.total_amount), 2) as avg_order_value
FROM behavior_ecommerce_orders e JOIN customers c ON e.cdp_customer_id = c.cdp_customer_id
WHERE c.loyalty_tier IS NOT NULL GROUP BY c.loyalty_tier ORDER BY avg_order_value DESC
```

**Query 7 — Engagement tier:**
```sql
SELECT e.engagement_tier, COUNT(DISTINCT e.cdp_customer_id) as customers,
  ROUND(AVG(c.predicted_ltv), 0) as avg_ltv
FROM behavior_engagement e JOIN customers c ON e.cdp_customer_id = c.cdp_customer_id
WHERE e.engagement_tier IS NOT NULL GROUP BY e.engagement_tier ORDER BY avg_ltv DESC
```

**Query 8 — Ecommerce by category affinity:**
```sql
SELECT c.category_affinity, ROUND(AVG(e.total_amount), 2) as avg_order,
  ROUND(AVG(c.predicted_ltv), 0) as avg_ltv
FROM behavior_ecommerce_orders e JOIN customers c ON e.cdp_customer_id = c.cdp_customer_id
WHERE c.category_affinity IS NOT NULL GROUP BY c.category_affinity ORDER BY avg_order DESC
```

### Phase 3: Segment Overlap & Unsegmented Population Queries

If segment overlap data is included, first discover all child segments. **IMPORTANT: Segments are nested inside subfolders of the parent segment.** The top-level `tdx sg list` may only show folders, not the actual segments. You MUST dig into each subfolder to find them:

```bash
tdx sg list --parent-segment "Parent Segment Name"
# If this returns folders/groups, list segments inside each subfolder:
tdx sg list --parent-segment "Parent Segment Name" --folder "Subfolder Name"
# Repeat for every subfolder to collect ALL segments
```

Then run these queries against the parent segment's child segment tables.

**Query 9 — Unsegmented customer profile:**
```sql
WITH all_segmented AS (
  SELECT DISTINCT cdp_customer_id FROM segment_a_table
  UNION SELECT DISTINCT cdp_customer_id FROM segment_b_table
  -- ... union all segment tables
)
SELECT COUNT(*) as unsegmented_count,
  ROUND(AVG(predicted_ltv), 0) as avg_ltv,
  ROUND(AVG(rewards_points), 0) as avg_points,
  ROUND(AVG(realised_ltv), 0) as avg_realised
FROM customers c
LEFT JOIN all_segmented s ON c.cdp_customer_id = s.cdp_customer_id
WHERE s.cdp_customer_id IS NULL
```

**Query 10 — Unsegmented breakdown by affinity:**
```sql
-- Same CTE as above
SELECT c.category_affinity as affinity, COUNT(*) as cnt,
  ROUND(AVG(c.predicted_ltv), 0) as avg_ltv
FROM customers c LEFT JOIN all_segmented s ON c.cdp_customer_id = s.cdp_customer_id
WHERE s.cdp_customer_id IS NULL AND c.category_affinity IS NOT NULL
GROUP BY c.category_affinity ORDER BY cnt DESC
```

**Query 11 — Unsegmented breakdown by churn risk:**
```sql
SELECT c.churn_prediction as label, COUNT(*) as cnt
FROM customers c LEFT JOIN all_segmented s ON c.cdp_customer_id = s.cdp_customer_id
WHERE s.cdp_customer_id IS NULL AND c.churn_prediction IS NOT NULL
GROUP BY c.churn_prediction ORDER BY cnt DESC
```

**Query 12 — Unsegmented breakdown by NBA action:**
```sql
SELECT c.next_best_action as action, COUNT(*) as cnt
FROM customers c LEFT JOIN all_segmented s ON c.cdp_customer_id = s.cdp_customer_id
WHERE s.cdp_customer_id IS NULL AND c.next_best_action IS NOT NULL
GROUP BY c.next_best_action ORDER BY cnt DESC
```

From these results, build segment recommendations:

**Segment recommendation patterns for unsegmented customers:**
- **"Silent Majority"** — Large group with Low/Very Low churn risk, stable but invisible. Tagged `coversUnsegmented: true`.
- **"Dormant Re-engagement"** — Unsegmented with High/Very High churn risk, actively churning undetected. Tagged `coversUnsegmented: true`.
- **Affinity-based segments** — Largest affinity cluster among unsegmented (e.g., "Streetwear Enthusiasts"). Tagged `coversUnsegmented: true`.
- **NBA-based segments** — Largest NBA action among unsegmented (e.g., "Cross-Sell Ready"). Tagged `coversUnsegmented: true`.

**Segment recommendation patterns from overlap analysis:**
- **"High-Value At-Risk"** — Overlap between At-Risk and High Value segments, needs unified retention. Tagged `coversUnsegmented: false`.
- **"App-First High Value"** — Small overlap worth dedicated mobile campaigns. Tagged `coversUnsegmented: false`.

**Also identify existing segment health issues** (stored as `fixRecs`):
- Conflicting-intent overlaps (e.g., At-Risk ∩ Freq Shoppers)
- Channel-based segments that should be filters (e.g., Email Opted-In)
- Low-overlap pairs that suggest segment rules need refinement

**Each recommendation must include:**

| Field | Description |
|-------|-------------|
| name | Proposed segment name |
| category | Retention / Growth / Win-Back / Re-engagement / New |
| targetSize | Estimated audience size from query results |
| avgLtv | Average LTV of target population |
| rationale | Why this segment should exist, grounded in data |
| suggestedRules | Key attribute filters as pseudo-SQL |
| priority | Critical / High / Medium |
| expectedImpact | What activating this segment would achieve |
| coversUnsegmented | Boolean — true if this segment targets customers not in any existing segment |
| color | Category color for the card |

### Phase 4: Analyze Findings & Build Campaign Recommendations

From the query results, identify **counterintuitive patterns** — these become:
1. **Key Finding cards** for Hidden Trends (icon, color, title, body, metric)
2. **Campaign recommendations** for Campaign Profitability (target, ROI, channel)

**Hidden Trend patterns to look for:**
- Value inversion: Lower tiers with higher LTV/AOV than upper tiers
- Churn paradox: Churned customers more valuable than active
- Channel gaps: Social outperforming email for specific actions
- Affinity sweet spots: Small segments with outsized per-customer value
- Engagement paradox: Medium engagement outperforming high engagement
- Campaign winners: Specific campaigns attracting highest-LTV audiences

**Each campaign recommendation must trace to a specific finding:**
```
Finding: "Bronze AOV ($1,352) beats Platinum ($1,264)"
  → Campaign: "Bronze Tier VIP Treatment" targeting 926K Bronze members
  → ROI calc: Target Size × Avg LTV × Conv Rate = Projected Revenue
```

**Conversion rate benchmarks:**
- Win-back: 10-20%
- Cross-sell: 5-15%
- Tier upgrade: 3-8%
- Content-based: 8-12%
- Loyalty reactivation: 12-18%

## One-Click Push Architecture

**The push strategy differs by environment:**

### Treasure Studio (render_react) — Clipboard Bridge

The clipboard bridge works in Treasure Studio because the agent and browser run on the same machine. The `render_react` sandbox blocks `fetch()` to localhost and `postMessage`, but clipboard polling via `pbpaste` works.

```
Dashboard Button Click
  → document.execCommand("copy") writes JSON command to clipboard
  → Background Node.js poller reads clipboard via pbpaste (every 1.5s)
  → Poller executes tdx sg push / tdx journey push
  → Button shows "Pushing..." then "Queued — Verify in AS"
```

### Treasure AI Studio (self-contained HTML) — URL Reveal

**Do NOT use the clipboard bridge in TAS.** TAS runs in a fully sandboxed iframe — `window.open`, `target="_blank"` links, localhost HTTP, and clipboard polling all fail silently. The agent and browser are on separate hosts (different machines), so the agent's clipboard is never the browser's clipboard.

**Instead, push all segments and journeys via CLI before rendering the dashboard**, then use the URL-reveal pattern for buttons:

```js
function showUrl(i, type, url){
  const box = document.getElementById('url-'+i);
  const txt = document.getElementById('url-'+i+'-text');
  txt.textContent = url;
  box.style.display = 'block';
  const range = document.createRange();
  range.selectNodeContents(txt);
  const sel = window.getSelection();
  sel.removeAllRanges();
  sel.addRange(range);
}
```

Each recommendation card gets two buttons (`✓ View Segment in AS` and `✓ View Journey in AS`) that call `showUrl(i, type, url)`. Below the buttons, include a hidden reveal div per card:

### Phase 5b: Generate Segment & Journey YAML Files

**For each `newSegmentRec`**, write a segment YAML file to `segments/(parent-segment-name)/Customer Intelligence/ci-(seg-key).yml`.

**IMPORTANT — Folder structure**: All CI segments and journeys MUST be placed inside a `Customer Intelligence` subfolder under the parent segment directory. This creates a "Customer Intelligence" folder in Audience Studio that organizes all CI-generated assets together. Create the folder if it doesn't exist:

**CRITICAL — Operator syntax reference** (field is ALWAYS `value` for most operators, NEVER `values`):

```yaml
# Equal — single string
operator:
  type: Equal
  value: "Senior Care"

# In — list of strings (field is `value`, NOT `values`)
operator:
  type: In
  value:
    - "Fish"
    - "Bird"
    - "Small Animal"

# GreaterEqual — numeric (NOT GreaterThanOrEqual)
operator:
  type: GreaterEqual
  value: 1

# Between — uses min/max fields (NOT a value list)
operator:
  type: Between
  min: 100
  max: 500

# IsNull — use not: true for "is not null"
operator:
  type: IsNull
  not: true
```

**Valid operator types**: `Equal`, `NotEqual`, `In`, `NotIn`, `Greater`, `GreaterEqual`, `Less`, `LessEqual`, `Between`, `IsNull`, `StartsWith`, `EndsWith`, `Contains`, `NotContains`, `TimeWithinLast`, `TimeWithinNext`, `TimeRange`, `TimeToday`

**Full segment YAML example:**

```yaml
name: "CI: Segment Name"
description: Description from recommendation
rule:
  type: And
  conditions:
    - type: Value
      attribute: field_name
      operator:
        type: Equal
        value: "value"
```

**After writing each segment YAML, validate it before rendering the dashboard:**
```bash
tdx sg validate "segments/(parent-segment-name)/Customer Intelligence/ci-(seg-key).yml"
```
Fix any validation errors before proceeding. Common mistakes:
- Using `values` instead of `value` on `In` operator (WRONG: `values:`, RIGHT: `value:`)
- Missing quotes on string values
- Aggregation type casing: `Count`, `Sum`, `Average`, `Min`, `Max` (capitalized, NOT lowercase)

**Behavior condition example** (use `type: Value` with `source`, `aggregation`, `filter` — NOT `type: Behavior`):

```yaml
# Count behavior rows matching a filter
- type: Value
  attribute: ""                              # empty string for behavior aggregations
  source: behavior_table_name                # behavior_<table> prefix required
  aggregation:
    type: Count                              # Count | Sum | Average | Min | Max (CAPITALIZED)
  operator:
    type: GreaterEqual
    value: 1
  filter:
    type: And
    conditions:
      - type: Column                         # use Column (NOT Value) inside filters
        column: column_name                  # use "column:" (NOT "attribute:")
        operator:
          type: Equal
          value: "filter_value"
```

**For EVERY recommendation**, also write an omni-channel, multi-stage journey YAML. Every recommendation gets both a "Create Segment" and "Build Journey" button — no exceptions. Set `hasJourney: true` on all recs.

**Journeys MUST be multi-stage and omni-channel** — never a single activation with a wait. The standard structure is 3 stages that escalate channel intensity:
- **Stage 1: Owned channels** (email + conditional app push or SMS) — lowest cost, highest ROAS
- **Stage 2: Paid amplification** (social retargeting + search) — for non-converters from Stage 1, with a decision point on LTV/tier/propensity to route high-value customers to more expensive placements
- **Stage 3: VIP last-chance offer** (SMS or exclusive email) — final rescue for customers who didn't respond to Stages 1–2

Each stage has its own `milestone` (who advanced) and `exit_criteria` (who converted). Customers who hit exit_criteria leave the journey; everyone else progresses to the next stage.

**Condition wait pattern** (branch on whether a condition is met within a timeout):
```yaml
- type: wait
  name: Wait for Purchase
  with:
    condition:
      segment: made-purchase         # references key from segments:
      next: Thank You Path           # met → this step
      timeout:
        duration: 14
        unit: day
        next: Timeout Path           # not met → this step
```
Each path MUST lead to a DIFFERENT action (otherwise use duration wait).

**CRITICAL journey YAML rules:**
1. **Journeys MUST have 2–3 stages** — never a single-stage journey. Follow the Stage 1 (owned) → Stage 2 (paid) → Stage 3 (VIP rescue) pattern. Omit Stage 3 only if the segment is small (< 200 customers).
2. **Each stage escalates channel intensity** — Stage 1 = email/app (lowest cost), Stage 2 = social/search (medium cost), Stage 3 = SMS/VIP exclusive (high-touch rescue). Never use the same channel type across all stages.
3. **Segment rules need And/Or wrapper** — `rule: { type: And, conditions: [...] }`, NOT bare `type: Value`
4. **Segment definitions use `description:`, NOT `name:`** — `name:` is not a valid field on inline journey segments
5. **Connection names + connector_config must be discovered** — run `tdx connection list` then `tdx connection schema "Name"` first, never guess
6. **First stage requires entry_criteria**, non-last stages need `milestone:`, all stages should have `exit_criteria:`
7. **Steps use `next:` + `with:`** — activation steps need `with: { activation: key }`, wait steps need `with: { duration, unit }`
8. **All branches must merge** — use a `merge` step, then `wait`, then `end`. Every branch must have an activation before merge.
9. **Wait after every activation** — API requires a wait step after activations (post-merge wait satisfies this for branched flows)
10. **Validate before pushing** — run `tdx journey validate` on each YAML, fix errors, then `tdx journey push --yes`
11. **Goal is recommended** — define inside `journeys: - state: draft:` with `name:` and `segment:`

**Connection discovery (MANDATORY before writing journeys):**
```bash
tdx connection list | head -20    # Find available connections
# Pick a connection of type treasure_data, sfmc, braze, etc.
# Use the exact connection NAME (second column), not the type
```

**Common journey patterns by recommendation type — adapt the 3-stage template:**

| Category | Stage 1 (Owned) | Stage 2 (Paid amplification) | Stage 3 (VIP rescue) |
|----------|----------------|------------------------------|----------------------|
| **Retention / Win-Back** | Personalized email + conditional app push (Has App?) | Facebook/Meta retarget + Search for High LTV | VIP SMS exclusive offer |
| **New → Repeat** | Post-purchase care tips email + app push | Social proof retarget (lookalike) + Search for high propensity | Exclusive offer SMS for non-converters |
| **Loyalty Upgrade** | Tier upgrade email + app push | Social retarget for High LTV + Search for Carry-On / category shoppers | VIP exclusive mailer or SMS |
| **Re-engagement** | Urgency email + conditional app push | Facebook DPA catalog retarget + Search conquest | Last-chance SMS with expiry |
| **Cross-sell** | Product recommendation email + app push for app users | Social lookalike for category affinity + Search for High AOV | Bundle offer SMS |

Decision point logic per stage:
- **Stage 1 branch**: Has App / Has Mobile Consent → App Push; else skip to merge
- **Stage 2 branch**: High LTV / High Propensity / Platinum tier → Search + Social; Standard → Social only
- **Stage 3**: No branch — single VIP activation for all remaining customers

### Phase 5c: Start the Clipboard Poller (Treasure Studio only)

**Skip this phase in Treasure AI Studio** — the clipboard poller doesn't work there (see One-Click Push Architecture above). In TAS, segments/journeys are already pushed via CLI before rendering; buttons use the URL-reveal pattern.

In Treasure Studio, write and start this poller before rendering:

Write a Node.js poller script (`ci-poller.js`) in the working directory. The poller uses a **file-based queue** (`/tmp/ci-queue.jsonl`) instead of relying solely on the clipboard, so rapid button clicks don't clobber each other. It **validates before pushing** and writes per-item result files so the dashboard can read back success/failure.

```javascript
const { execSync } = require('child_process');
const fs = require('fs');
const path = require('path');

const BASE_DIR = process.env.CI_BASE_DIR || process.cwd();
const QUEUE_FILE = '/tmp/ci-queue.jsonl';
const RESULT_DIR = '/tmp/ci-results';

// Ensure result directory exists
if (!fs.existsSync(RESULT_DIR)) fs.mkdirSync(RESULT_DIR, { recursive: true });

let lastClip = '';
let processing = false;

// Step 1: Clipboard watcher — appends new commands to the queue file
setInterval(() => {
  let clip;
  try { clip = execSync('pbpaste', { encoding: 'utf8' }).trim(); } catch { return; }
  if (clip === lastClip) return;
  lastClip = clip;

  let cmd;
  try { cmd = JSON.parse(clip); } catch { return; }
  if (!cmd.__ci_push || !cmd.id) return;

  // Append to queue (one JSON object per line)
  fs.appendFileSync(QUEUE_FILE, JSON.stringify(cmd) + '\n');
  console.log(`[${new Date().toISOString()}] Queued: ${cmd.action} ${cmd.name} (${cmd.id})`);
}, 1500);

// Step 2: Queue processor — drains one item at a time (no concurrent pushes)
setInterval(() => {
  if (processing) return;
  if (!fs.existsSync(QUEUE_FILE)) return;

  const lines = fs.readFileSync(QUEUE_FILE, 'utf8').trim().split('\n').filter(Boolean);
  if (lines.length === 0) return;

  // Take first item, rewrite queue without it
  const cmd = JSON.parse(lines[0]);
  fs.writeFileSync(QUEUE_FILE, lines.slice(1).join('\n') + (lines.length > 1 ? '\n' : ''));
  processing = true;

  const writeResult = (id, status, message) => {
    fs.writeFileSync(path.join(RESULT_DIR, `${id}.json`), JSON.stringify({ status, message, ts: Date.now() }));
  };

  // Find YAML file — search recursively in all segments/ subdirectories (including Customer Intelligence/)
  let file;
  const segDir = path.join(BASE_DIR, 'segments');
  const findYaml = (dir, relBase) => {
    if (!fs.existsSync(dir)) return;
    for (const entry of fs.readdirSync(dir)) {
      const full = path.join(dir, entry);
      const rel = path.join(relBase, entry);
      if (fs.statSync(full).isDirectory()) {
        findYaml(full, rel);
        if (file) return;
      } else if (entry === `${cmd.name}.yml`) {
        file = rel;
        return;
      }
    }
  };
  findYaml(segDir, 'segments');
  if (!file) {
    console.error(`[${new Date().toISOString()}] File not found: ${cmd.name}.yml`);
    writeResult(cmd.id, 'error', `File not found: ${cmd.name}.yml`);
    processing = false;
    return;
  }

  const isJourney = cmd.action === 'push-journey';

  // Validate BEFORE pushing
  const validateCmd = isJourney ? `tdx journey validate "${file}"` : `tdx sg validate "${file}"`;
  try {
    execSync(validateCmd, { cwd: BASE_DIR, timeout: 30000, encoding: 'utf8' });
  } catch (err) {
    console.error(`[${new Date().toISOString()}] Validation FAILED: ${err.message}`);
    writeResult(cmd.id, 'error', 'Validation failed');
    processing = false;
    return;
  }

  // Push (only if validation passed)
  const pushCmd = isJourney ? `tdx journey push "${file}" --yes` : `tdx sg push --yes "${file}"`;
  try {
    const result = execSync(pushCmd, { cwd: BASE_DIR, timeout: 120000, encoding: 'utf8' });
    console.log(`[${new Date().toISOString()}] Pushed: ${cmd.name}`);
    // Extract console URL from push output if present
    const urlMatch = result.match(/https:\/\/console[^\s]+/);
    writeResult(cmd.id, 'done', urlMatch ? urlMatch[0] : 'Pushed successfully');
  } catch (err) {
    console.error(`[${new Date().toISOString()}] Push error: ${err.message}`);
    writeResult(cmd.id, 'error', 'Push failed — check poller log');
  }
  processing = false;
}, 2000);

console.log(`[${new Date().toISOString()}] CI Poller started (queue-based, validate-then-push). Base: ${BASE_DIR}`);
```

**Key improvements:**
- **File-based queue** (`/tmp/ci-queue.jsonl`): rapid button clicks append to the queue instead of overwriting each other on the clipboard
- **Per-item result files** (`/tmp/ci-results/{id}.json`): the dashboard polls these to show real success/failure status, not a blind timeout
- **Sequential processing**: only one push runs at a time — no clipboard race conditions
- **Validate-then-push**: blocks invalid YAMLs from reaching the API
- **Auto-discovers file path**: searches all `segments/*/` subdirectories, so it works for any parent segment without hardcoding
- **Distinct error states**: `ci-error-notfound`, `ci-error-validation`, `ci-error-push` for debugging

Start with: `nohup node ci-poller.js > /tmp/ci-poller.log 2>&1 &`

They use the `triggerPush` clipboard bridge function (see One-Click Push Architecture). The buttons must appear below the rationale text, before the expanded rules section:

```jsx
// REQUIRED state at component top level:
const [pushState, setPushState] = useState({}); // {id: 'idle'|'pushing'|'done'}

// triggerPush function — REQUIRED. Copies JSON command to clipboard for the queue-based poller.
// The render_react sandbox cannot read files or clipboard back, so we use a timeout.
// The poller validates before pushing and logs errors — if the button shows "Queued" but
// nothing appears in Audience Studio, check /tmp/ci-results/{id}.json or the poller log.
const triggerPush = (id, action, name) => {
  if (pushState[id] === 'pushing' || pushState[id] === 'done') return;
  const cmd = JSON.stringify({__ci_push:true, action, name, id});
  const ta = document.createElement('textarea');
  ta.value = cmd;
  ta.style.cssText = 'position:fixed;left:-9999px';
  document.body.appendChild(ta);
  ta.select();
  try { document.execCommand('copy'); } catch(e) {}
  document.body.removeChild(ta);
  setPushState(prev => ({...prev, [id]: 'pushing'}));
  // Timeout covers: queue wait (if items ahead) + validate (~3s) + push (~10s)
  // Shows "Queued" rather than false "Created" — user should verify in Audience Studio
  setTimeout(() => setPushState(prev => ({...prev, [id]: 'done'})), 30000);
};

// REQUIRED buttons inside EVERY recommendation card (after rationale, before expanded rules):
<div style={{display:'flex', gap:8, marginTop:8}}>
  <button onClick={(e) => { e.stopPropagation(); triggerPush(`seg-${i}`, 'push-segment', rec.segKey); }}
    disabled={pushState[`seg-${i}`]==='pushing'||pushState[`seg-${i}`]==='done'}
    style={{
      padding:'6px 14px', borderRadius:8, fontSize:11, fontWeight:700, border:'none', cursor:'pointer',
      background: pushState[`seg-${i}`]==='done' ? '#22c55e' : pushState[`seg-${i}`]==='pushing' ? '#f59e0b' : 'linear-gradient(135deg,#6366f1,#8b5cf6)',
      color:'#fff', opacity: pushState[`seg-${i}`]==='pushing' ? 0.8 : 1
    }}>
    {pushState[`seg-${i}`]==='done' ? '✓ Queued — Verify in AS' : pushState[`seg-${i}`]==='pushing' ? '⏳ Pushing...' : '▶ Create Segment'}
  </button>
  <button onClick={(e) => { e.stopPropagation(); triggerPush(`j-${i}`, 'push-journey', rec.journeyKey); }}
    disabled={pushState[`j-${i}`]==='pushing'||pushState[`j-${i}`]==='done'}
    style={{
      padding:'6px 14px', borderRadius:8, fontSize:11, fontWeight:700, border:'none', cursor:'pointer',
      background: pushState[`j-${i}`]==='done' ? '#22c55e' : pushState[`j-${i}`]==='pushing' ? '#f59e0b' : 'linear-gradient(135deg,#0ea5e9,#6366f1)',
      color:'#fff', opacity: pushState[`j-${i}`]==='pushing' ? 0.8 : 1
    }}>
    {pushState[`j-${i}`]==='done' ? '✓ Queued — Verify in AS' : pushState[`j-${i}`]==='pushing' ? '⏳ Pushing...' : '▶ Build Journey'}
  </button>
</div>
```

## Best Practices

1. **Single render_react call** — never use multiple render_react calls, they replace each other
2. **Always discover schema first** — never assume column names
3. **Check column population** — COUNT(column) before using it in dashboards
4. **Run queries in parallel** — all trend queries and segment overlap queries are independent
6. **Look for counterintuitive patterns** — the value is in surprises
7. **Ground campaigns in data** — every recommendation traces to a specific finding
8. **Conservative conversion rates** — use low end of benchmarks
9. **Glassmorphism everywhere** — use GlassCard, Badge, MiniSpark, translucent callouts. No flat white cards or Tailwind `bg-white`/`dark:bg-gray-900` patterns.
10. **Hover interactions** — insight and campaign cards lift on hover with border glow
11. **Click to expand** — recommendation cards expand to show rules and impact on click
12. **Reset sub-tab on page switch** — `switchPage` must call `setSubTab(0)`
13. **Always analyze unsegmented customers** — if segment overlap is included, query unsegmented population and include at least 2 recommendations that target customers not in any segment (tagged `coversUnsegmented: true`)
14. **Include existing segment health** — flag conflicting overlaps, channel-as-segment anti-patterns, and low-overlap pairs that suggest refinement
15. **Generate YAML files and push before rendering (TAS)** — in Treasure AI Studio, push all segments and journeys via CLI (`tdx sg push`, `tdx journey push`) before rendering the dashboard. Buttons link to the live AS URLs via the URL-reveal pattern.
16. **Start clipboard poller (Treasure Studio only)** — in Treasure Studio, launch `ci-poller.js` in the background before rendering. In TAS, skip the poller entirely and use URL-reveal buttons instead.
17. **Use `type: Value` for behaviors** — behavior conditions use `type: Value` with `attribute: ""`, `source`, `aggregation`, and `filter` (NOT `type: Behavior`)
18. **Validate all YAMLs before rendering** — run `tdx sg validate` on every segment YAML and `tdx journey validate` on every journey YAML after writing. Fix errors before rendering the dashboard.
19. **Operator names match the authoritative list** — use `GreaterEqual` (NOT `GreaterThanOrEqual`), `Between` uses `min:`/`max:` fields (NOT a `value` list). Full list: `Equal`, `NotEqual`, `In`, `NotIn`, `Greater`, `GreaterEqual`, `Less`, `LessEqual`, `Between`, `IsNull`, `StartsWith`, `EndsWith`, `Contains`, `NotContains`, `TimeWithinLast`, `TimeWithinNext`, `TimeRange`, `TimeToday`.
20. **Journey segment rules need And/Or wrapper** — journey inline segments use `rule: { type: And, conditions: [...] }`, not bare `type: Value`
21. **Journey segments use `description:`, NOT `name:`** — inline segment definitions in journeys do not have a `name:` field
22. **Discover connections + connector_config before writing journeys** — run `tdx connection list` then `tdx connection schema "Connection Name"` to get required `connector_config` fields. Never guess connection names.
23. **Journey stages need entry_criteria + milestone + exit_criteria** — `entry_criteria` is required on the first stage, `milestone` is required on non-last stages, `exit_criteria` is recommended on all stages
24. **Journey steps use `next:` + `with:`** — every branch must have an activation before merge. All branches must converge through a merge step (not directly to end).

## Common Issues

### Some columns are all-NULL
Check with COUNT(column) first. Adapt the dashboard to only show data that exists. If first_name is null, use email as the identity.

### Campaign Profitability numbers seem unrealistic
- Validate target sizes against actual query counts
- Use conservative conversion benchmarks (low end)
- Note data quality gaps explicitly rather than assuming

### Component too large for render_react
Keep the component under ~500 lines of JSX. If larger, simplify chart configurations by extracting common tooltip/axis configs into shared variables at the top.
